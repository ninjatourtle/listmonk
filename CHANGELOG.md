# История изменений Listmonk

## [Unreleased] - Трекинг ответов по In-Reply-To через POP3

### ✨ Новое
- «Тихий» трекинг ответов без нестандартных заголовков: сопоставление входящих писем по In-Reply-To/References с нашим Message-ID.
- POP3-сканер для ящиков отправителя в «Личностях» (Personas): ответы принимаются прямо на исходные ящики.

### 🔧 Изменения (backend)
- Гарантированная генерация и сохранение Message-ID при отправке; запись в `campaign_sends.message_id` и отметки ответа в `campaign_sends.reply_at`.
- Запись событий ответа в `campaign_replies` (campaign_id, subscriber_id, send_id, subject, snippet, headers).
- Новые модули: `internal/replies/manager.go`, `internal/replies/mailbox/pop.go`; метод `Core.RecordReply` для сохранения.
- Инициализация POP3-сканеров из настроек персон при `reply.enabled = true`.
- Вынесен общий планировщик слотов (`internal/manager/scheduler.go`); распределение по окну с джиттером теперь единообразно для кампаний и прогрева.
- `internal/manager/pipe.go`: переработан `NextSubscribers` для расписаний — без блокирующих `time.Sleep`, с повторной постановкой через `enqueueAfter`, хранением состояния слотов и единым методом выбора persona.
- Обновлены SQL утилиты для SMTP статистики: добавлен инкремент `smtp-increment`, подготовительные изменения для жёстких лимитов.
- SMTP лимиты: счётчики `SentToday` восстанавливаются из `smtp_stats` при старте, превышение лимита возвращает типизированную ошибку и автоматически приостанавливает кампанию.
- Dashboard: переработаны графики и KPI — сервер теперь отдаёт агрегированные `campaign_sends` / `campaign_replies` / `campaign_bounces`, фронтенд строит метрики без тяжёлых выборок.
- Dashboard: блок SMTP показывает фактическое исчерпание дневных лимитов (прогресс, статус) и подсвечивает остановленные аккаунты.
- SMTP Stats: добавлены визуальные индикаторы дневного лимита и подсветка серверов, достигших предела.

### ⚙️ Настройки

  `pop_enabled`, `pop_host`, `pop_port`, `pop_username`, `pop_password`,

### ⚠️ Совместимость

## [2025-01-17] - КРИТИЧЕСКОЕ ИСПРАВЛЕНИЕ: Проблемы с часовыми поясами и JavaScript ошибки в расписании прогрева

### 🚨 ВАЖНОЕ ИСПРАВЛЕНИЕ ДЛЯ РАБОТЫ С РАСПИСАНИЕМ ПРОГРЕВА

#### ⚠️ ПРОБЛЕМЫ, КОТОРЫЕ БЫЛИ ИСПРАВЛЕНЫ:
**"Внутренняя ошибка сервера" при переходе в расписание прогрева и JavaScript ошибки**

- **Проблема 1**: SQL запросы использовали `due_at::date = $2`, что вызывало проблемы с часовыми поясами
- **Проблема 2**: JavaScript ошибка "Cannot read properties of null (reading 'constructor')" в frontend
- **Проблема 3**: Неправильная обработка null/undefined значений в компонентах
- **Проблема 4**: Сервер работал в UTC, а клиент в другом часовом поясе

**Обновлены все запросы для корректной работы с часовыми поясами:**
- `warmcloud-sched-list-by-day`: Заменен `due_at::date = $2` на `due_at >= $2::date AND due_at < ($2::date + INTERVAL '1 day')`
- `warmcloud-sched-count-pending-today`: Исправлен для использования диапазона дат
- `warmcloud-sched-delete-day-pending`: Обновлен для корректной работы с часовыми поясами

## [2025-01-15] - РЕВОЛЮЦИОННОЕ ОБНОВЛЕНИЕ: Полностью переработанная логика прогрева сервера

### 🚀 КРИТИЧЕСКОЕ ОБНОВЛЕНИЕ СИСТЕМЫ ПРОГРЕВА
**Полностью переработана логика прогрева сервера согласно новым требованиям**

#### ✨ НОВАЯ ЛОГИКА ПРОГРЕВА:

**1. Автоматическое формирование расписания при включении прогрева:**
- При включении прогрева сервер автоматически создает полное расписание отправок на день
- Количество отправок в расписании соответствует дневному лимиту
- Расписание формируется с учетом рабочих часов

**2. Умное распределение отправок по дню:**
- Отправки равномерно распределяются по всему дню
- Учитываются настройки рабочих часов (глобальные и персональные для сервера)
- Добавлен jitter (случайное отклонение 0-59 секунд) для естественного распределения
- Поддержка множественных временных окон (например: "9-12,14-18")

**3. Автоматическое заполнение адреса отправителя:**
- При создании расписания автоматически заполняется поле "Адрес отправителя"
- Адрес берется из настроек кампании, указанной в настройках прогрева
- Приоритет: кампания.from_email → сервер.username → заголовки → fallback

**4. Полная поддержка личностей (personas):**
- Если в настройках кампании указано использование личностей, система автоматически использует личности
- Адреса отправителей берутся из настроек личности в равных пропорциях
- Автоматическая ротация между адресами личности при создании расписания
- Проверка разрешений SMTP серверов для каждой личности

### 📋 Логика статусов и процента чтения

#### Как работает система статусов:
1. **"Ожидает" (pending)** - письмо запланировано к отправке
2. **"Отправлено" (done)** - письмо успешно отправлено
3. **"Прочитано" (read)** - письмо отправлено И подтверждено через WarmCloud API (submit)

#### Логика процента чтения:
- **Настройка "Процент чтения"** (например, 65%) определяет, какой процент от отправленных писем будет отмечен как "прочитанные"
- **Алгоритм**: Для каждого отправленного письма система случайно решает (с вероятностью равной проценту чтения), отправлять ли подтверждение в WarmCloud API
- **Пример**: При 65% чтения из 100 отправленных писем примерно 65 будут отмечены как "прочитанные"

#### Почему может быть расхождение:
- **Настройки системы**: Процент чтения в настройках сервера (65%)
- **Postmaster Mail.ru**: Показывает реальную статистику открытий (81%)
- **Разница**: Система имитирует чтение по настройкам, а не отражает реальную статистику открытий

#### Обновление статусов:
- Статус обновляется с "Отправлено" на "Прочитано" автоматически каждые 10 секунд
- Система ищет записи со статусом "Отправлено", которые имеют успешный submit в WarmCloud API
- Найденные записи автоматически получают статус "Прочитано"
